# Provider-side spending authority and Credit pauses

**Status:** Accepted

Supersedes the paid-allowance parts of the governing media operating architecture ([#47](https://github.com/phenome/vaporstats/issues/47#issuecomment-5627349676), "Initial operating envelope" and "Trigger, state and failure boundaries"), the experiment specification ([#51](https://github.com/phenome/vaporstats/issues/51), "Search, source access, and budgets" and the pricing confirmation in "Testing Decisions"), and the [#66](https://github.com/phenome/vaporstats/issues/66) allowance decision, as decided in [#71](https://github.com/phenome/vaporstats/issues/71) and implemented in [#72](https://github.com/phenome/vaporstats/issues/72).

## Context

Paid media work (article extraction, Overview synthesis and embeddings) ran under a nonrenewing US$5 lifetime allowance. Every request first reserved a conservative upper bound, and work was refused once settled charges plus active reservations reached the allowance. A runtime pricing and capability confirmation also had to match before any paid work started. Once the allowance was used, useful work was refused permanently, and unattended ingestion could not continue.

## Decision

**The provider holds spending authority.** VaporStats keeps no internal budget. The spending limit is the credit or billing limit that the maintainer configures with each paid provider: the Google project's Prepay balance and spend cap for Gemini. No code path reserves, sums or compares spend before submitting. The pricing and capability confirmation is no longer a runtime gate; paid work needs only a configured provider key.

**Paid work waits in a durable queue.** The existing paid-job ledger becomes the **Paid-work queue** rather than a separate queue service. Each item carries its entity, stage, input identity, enqueue time, attempt count, next attempt time, provider and status. Article text is fetched only when an extraction item is submitted and is never stored, so waiting work holds no source text. Each tick, every active provider takes items in rounds, and each entity contributes its oldest ready item per round. Entities are ordered first by their last turn, oldest first, which the queue records durably, then by the enqueue time of their oldest waiting item, then by entity. Per-tick submission counts are bounded; because turns carry across ticks, every entity with ready work takes a turn within as many ticks as the entity count divided by the per-tick bound, rounded up, however many entities wait.

**One classifier per paid provider.** Every provider response is classified once into success, transient, Credit pause, definite refusal, uncertain, or missing configuration, and every submission and poll path acts on that class:

- A **Credit pause** (Gemini HTTP 402 for depleted Prepay credits, or a 429 that reports an exceeded spending cap) pauses the provider with its reason and time. Every queued item of that provider stays queued, with no attempt counted and no failure recorded. Other providers are unaffected. The pause lasts until the next daily credit check.
- A **transient** failure (network failure before the request was sent, timeout responses, 408, 5xx, 429 rate limits, or a batch the provider expired or cancelled without running it) keeps the item queued. It retries at the next tick, then with doubling backoff capped at 24 hours, never before `Retry-After`. It never becomes a failure.
- A **definite refusal** (an invalid request, output that fails validation, or input over the per-request cap) refuses the item for its input identity. Only a request that is itself unacceptable is refused; an error about the project is a configuration pause. Only an authorized correction set re-attempts it, and existing still-supported output stays active.
- An **uncertain** submission (sent, but without an answer) is never resubmitted blindly and is reported in the uncertain count.
- **Missing configuration** pauses the provider with reason `missing_key` while no key is configured, and fails nothing. A project-level error pauses the provider until the next daily credit check and also fails or refuses nothing: a rejected key (`rejected_key`: HTTP 401 or 403, or a 400 that reports an invalid or expired key), a failed project precondition such as billing that is not enabled (`failed_precondition`), or a model the provider no longer serves (`model_unavailable`: HTTP 404 on a token count or submission). A poll error about one batch, such as an unknown batch, leaves that item uncertain.

**A daily credit check resumes paused providers.** It runs in the first ingestion tick at or after 06:00 UTC on each UTC day, whether or not paid work waits, recorded by a durable checkpoint, so a restart neither repeats nor skips it and a missed earlier day is never made up. Google documents no endpoint that reports Prepay balance or spend-cap headroom, so the check lifts a Gemini pause and submits the oldest ready embedding item as a probe. When no paid work waits, the check only records its run and lifts the pause, and the next submission is the probe. Another Credit pause response pauses Gemini again until the next day.

**Cost is reported, never enforced.** Each settled item records its cost and its source. Gemini cost is returned token usage at the documented batch price, marked as estimated. An item settled without provider usage records zero, marked unknown: neither token caps nor a retained reservation is presented as spend, and a retained row keeps its reserved amount and reservation flag. Processing summaries and the tick log report month-to-date (UTC calendar month) and all-time cost per provider, labeled reporting-only, plus the uncertain count.

**Retired accounting is kept as history.** Existing paid-job rows keep their reserved amounts, reservation flags, settled charges and statuses. Retained uncertain jobs stay uncertain, and their reservations do not count as cost. The queue migration marks every row it carries over as retained, and the queue never deletes, submits or requeues a retained row, whether or not its input still matches current work: a retained `reserved` row was never authorized under the queue. An open authorization queues that work as a new item of its own. A batch a retained row already submitted is still polled and settled; if the provider ended it without output, the row ends `stale` rather than returning to the queue.

## Consequences

- Useful work is no longer refused for budget reasons. A depleted balance delays work until the maintainer adds credit, and the daily check finds it.
- Spend is bounded only by the provider-side limits, which the maintainer must keep configured. VaporStats reports cost so it can be compared with those limits.
- Corrections and later provider slices enter the same queue under the same Credit pauses; each new provider adds its own classifier and daily check.

## Amendment (2026-11-18): uncertain resends, unrecognized client errors and embedding order

Decided in [#80](https://github.com/phenome/vaporstats/issues/80) for every paid provider. It changes the uncertain and refusal classes above, and the parent failure-class table of [#71](https://github.com/phenome/vaporstats/issues/71).

- **Uncertain items are resent automatically.** An item is uncertain when its provider may have received it and the outcome is unknown: a timeout or lost connection after sending, a restart while it was in flight, an error after the provider accepted it, an error a poll reports about its batch, or a Gemini batch that the provider accepted and that then ended `BATCH_STATE_FAILED` with a generic error, which was a refusal before. An uncertain item is no longer held for a correction set. It returns to the Paid-work queue and is resent under the transient backoff and the Credit pauses, through the same queue and the same backoff, never a separate retry mechanism. At three uncertain outcomes (`MAX_UNCERTAIN_SENDS`) for one item and input identity with no definite outcome (a success, a refusal or a stale answer) between them, the item ends `uncertain_exhausted`, and only a correction set resends it. A transient failure, a Credit pause or a configuration pause does not end the streak. A send with a new input identity starts a fresh streak, but six uncertain outcomes in one item's lifetime (`MAX_UNCERTAIN_OUTCOMES_PER_JOB`), across all its input identities, also end it `uncertain_exhausted`, so possibly charged resends stay bounded. A Gemini batch that succeeded with an error in place of its one response is still a definite refusal.
- **Every attempt is recorded.** Each send is an attempt in `media_processing_attempts`, with its provider, input identity, send time, outcome, Gemini batch id or OpenRouter generation id and routing, usage and cost. A job keeps the sum of its attempts' cost. Month-to-date and all-time cost sum every attempt, each in the UTC month its cost settled in, on the provider it was sent to. A job recorded before attempts existed reports its own values as its one attempt and gains that attempt row when it is sent or polled again, so no earlier charge leaves the report. A resent item whose work then needs no provider ends `stale` instead of being removed, so its attempts stay reported.
- **An unrecognized 4xx pauses the provider.** A 4xx that the provider's classifier does not recognize is a configuration problem on the project side. It pauses that provider with reason `unrecognized_client_error` until the next daily credit check, keeps every queued item, and never refuses an item. The item that triggered it also counts a failure, with the transient backoff, and the daily Gemini probe skips items in backoff, so one item cannot take the provider's first turn after every check. The third such pause one item triggers for one input identity (`MAX_CLIENT_ERROR_PAUSES`) ends it `client_error_exhausted`: not a refusal, resent only by a correction set, and it triggers no more pauses. Refusal is limited to the documented item-specific classes: content and moderation refusals, input over the cap, invalid output, and a documented invalid-request shape tied to the item (Gemini's 400 `INVALID_ARGUMENT`, OpenRouter's 400). A poll error about one batch stays uncertain for that batch.
- **Embeddings follow the Overview they embed.** A game whose Overview rebuild is queued or waiting, or which has extraction work waiting that will rebuild it, holds its embedding work until the new Overview is active: such work is neither queued nor submitted for an Overview about to be replaced. Work behind a provider pause still waits, since the pause lifts. An extraction whose article is on an outlet with an Outlet denial is refused as `outlet_denied` instead of waiting, because the denial is permanent, so it never holds its game's Overview or embeddings.

## Amendment (2026-11-18): paused providers are rechecked when the application starts

A pause lifted only at the daily credit check, so a fix deployed for a configuration pause still waited up to a day: on 2026-11-18 a cut-off Overview paused OpenRouter as `output_truncated` at 19:45 UTC, and the deployed fix could not resume text generation before 06:00 UTC the next day.

- **Startup recheck.** On the first ingestion tick after the application starts, every paused provider gets the check the daily credit check runs: OpenRouter's current-key check, and for Gemini, which has no credit endpoint, the probe rule (every pause but a missing key's lifts, and the next submission probes credit). A pause whose cause is gone lifts; otherwise it stays, with its recorded check time and outcome.
- **The daily schedule is unchanged.** The recheck runs no daily media run and never records the daily checkpoint, so the daily check and the daily media run still run at their time. When the daily check is due on that first tick, it covers the recheck.
- **Item counts are unchanged.** Each item's count of client-error pauses, and its uncertain streak, stay as they were, so an item that triggered a pause keeps that strike after the pause lifts.
- **A restart is the trigger.** One process keeps one database handle, so the recheck runs once per handle; nothing durable records it, and every restart runs it again. A provider still out of credit is paused again by the check or by its probe, which costs at most one probe submission per restart.
